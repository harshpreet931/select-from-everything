<InShort>
**ACID** is four promises about transactions. **atomicity**: all of it or none of it. **consistency**: every commit leaves the data valid, but only by the rules you wrote down. **isolation**: concurrent transactions don't trip over each other, to a degree you choose. **durability**: once COMMIT returns, a crash can't take it back. two of them postgres keeps completely. the other two are partly your job.
</InShort>

## the picture

you know how ACID gets recited like one thing, a seal of quality on a database? it's four different promises, kept by four different parts of the system, and each one has an edge where it stops.

think of a bank transfer as a sealed envelope. atomicity: the envelope is delivered whole or not at all. consistency: the bank won't accept an envelope that breaks its rules, but only the rules printed on the form. isolation: two clerks working at once don't mix up each other's envelopes, mostly. durability: once the bank stamps your receipt, a fire in the back office doesn't undo it.

## atomicity: all or nothing

a transfer is two updates. if the second one fails, the first must not count. bank's CHECK says a balance can't go negative, and carol has 0.00:

```sql run db=bank errors=continue
BEGIN;
UPDATE accounts SET balance = balance + 50.00 WHERE id = 1;
UPDATE accounts SET balance = balance - 50.00 WHERE id = 3;
COMMIT;
SELECT id, owner, balance FROM accounts WHERE id IN (1, 3) ORDER BY id;
```

alice's +50.00 ran (`UPDATE 1`) and is gone anyway. the COMMIT came back as ROLLBACK, because the transaction was already [aborted](/learn/transactions/begin-commit-rollback) by the error. nothing had to be undone, either: postgres just records that the transaction aborted, and every reader skips the versions it wrote ([an UPDATE is an INSERT](/learn/mvcc/update-is-insert) shows the leftover row).

## consistency: your rules, written down

the C is the odd one out. the database can only keep data "valid" by rules it knows: types, NOT NULL, CHECK, UNIQUE, foreign keys, triggers. above, the CHECK did that job. but bank's real rule, that alice and bob hold 200.00 between them, isn't written anywhere the database can see:

```sql run db=bank
UPDATE accounts SET balance = balance + 50.00 WHERE id = 1;
SELECT sum(balance) AS alice_and_bob FROM accounts WHERE id IN (1, 2);
```

250.00, committed, no complaint. that's the honest version of the C: the database keeps the [constraints you declare](/learn/design/constraints), and your code keeps everything else. the other three letters are what make it possible for your code to do that: a transaction that goes from valid to valid won't be half-applied (A), disturbed (I), or forgotten (D).

## isolation: it depends

the I promises that concurrent transactions don't see each other's half-finished work. postgres keeps that part at every level: it [never shows uncommitted data](/learn/transactions/anomalies). but full isolation means the result is the same as running the transactions one at a time, and at the default level, READ COMMITTED, it isn't always: lost updates, read skew and write skew all get through. only SERIALIZABLE promises the textbook I, and it keeps the promise by sometimes failing a transaction with 40001. [isolation levels](/learn/transactions/isolation-levels) is the menu.

## durability: COMMIT means it

when COMMIT returns, the transaction's WAL record is already flushed to disk. the table pages it changed may still be only in memory; after a crash, postgres replays the WAL to put them back. this capture runs one transfer to the end, starts a second one, and kills the server in the middle:

<Predict question="T2 had taken 30.00 from bob but not committed when the server was killed. after the restart, what does bob have?" options={["120.00: T2's half is on disk", "150.00", "the server won't start"]} answer={1}>
```sql
-- T1: committed: alice 50.00, bob 150.00
/* T2 */ BEGIN;
/* T2 */ UPDATE accounts SET balance = balance - 30.00 WHERE id = 2;
-- pg_ctl stop -m immediate, then start
SELECT id, owner, balance FROM accounts ORDER BY id;  -- bob = ?
```
<Explain>
150.00. T1's transfer had its commit record flushed before COMMIT returned, so recovery replays it and it's all there. T2's update never even reached the disk: the capture's WAL on disk ends at T1's commit record, and T2's record was still in memory when the server died. and if it had made it to disk, it wouldn't matter: T2 has no commit record, so after the restart it counts as aborted and its version of bob is invisible. atomicity and durability, from the same log.
</Explain>
</Predict>

durability has edges too. this was a process crash: the operating system kept running, and so did the disk. postgres's promise rests on the disk telling the truth when it says a write is done (`fsync`). it doesn't cover a dead disk (that's [backups](/learn/wal/backups-and-pitr) and [replicas](/learn/wal/streaming-replication)), a `DROP TABLE` you committed on purpose, or `synchronous_commit = off`, which lets COMMIT return before the flush and can lose the last few transactions in a crash ([what COMMIT waits for](/learn/wal/commit-path)).

<Gotcha title="the C in ACID isn't the C in CAP">
consistency in ACID means "obeys the rules". consistency in CAP (and in "eventual consistency") means "every reader sees the latest write". same word, unrelated ideas. a single postgres server is consistent in both senses. a read replica can be ACID-consistent and still return yesterday's balance. [CAP and PACELC](/learn/scale/cap-and-pacelc) has the other one.
</Gotcha>

<Interview q="what does each letter of ACID guarantee, and which ones does the database alone enforce?">
atomicity: a transaction's changes all happen or none do (in postgres: a commit record in the WAL decides, and an aborted transaction's row versions are ignored). consistency: each commit leaves the data satisfying the declared constraints; any rule not declared is the application's job. isolation: concurrent transactions don't interfere, but how much depends on the isolation level; only SERIALIZABLE gives full isolation, and the default READ COMMITTED allows lost updates and write skew. durability: after COMMIT returns, the change survives a crash, because the WAL was flushed first. the database alone fully enforces A and D; C and I are shared with the application.
</Interview>

<Keylines>
- atomicity: a failed statement aborts the whole transaction. COMMIT becomes ROLLBACK.
- consistency is only as good as the constraints you declare.
- isolation at the default level is partial. SERIALIZABLE is the full promise.
- durability: COMMIT returns after the WAL is on disk. a crash replays it.
- A and D are postgres's job. C and I are shared with your code.
</Keylines>
