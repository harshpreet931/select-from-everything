<InShort>
an **advisory lock** is a lock on a number you pick. postgres keeps it in the same lock manager as its own locks, but never takes one for you and never checks it against any row: it means whatever your code agrees it means. **pg_advisory_lock** holds it for the session, through COMMIT and ROLLBACK, until you unlock or disconnect. **pg_advisory_xact_lock** holds it until the transaction ends. **pg_try_advisory_lock** never waits: it answers true or false.
</InShort>

## the picture

you know the cron job that runs on three app servers, and the night it ran three times and sent everyone three invoices? you need a mutex that all three servers can see. they all talk to the same database, so the database can hold it.

think of a numbered "busy" sign at a reception desk (the lock manager). nobody checks what you do while you hold sign 42. the only rule is that two people can't hold it at once, and everyone agrees that sign 42 means "the nightly report".

## the three questions each function answers

| function | if someone else holds it | released at |
| --- | --- | --- |
| `pg_advisory_lock(k)` | waits | `pg_advisory_unlock(k)`, or the session ending |
| `pg_try_advisory_lock(k)` | returns false at once | the same |
| `pg_advisory_xact_lock(k)` | waits | COMMIT or ROLLBACK, nothing else |
| `pg_try_advisory_xact_lock(k)` | returns false at once | COMMIT or ROLLBACK |

each has a `_shared` twin: shared holders don't block each other, only an exclusive one. the key is one bigint or two ints. here's one taken, seen in pg_locks, and given back:

```sql run
SELECT pg_advisory_lock(42);
SELECT locktype, classid, objid, objsubid, mode, granted
FROM pg_locks WHERE locktype = 'advisory';
SELECT pg_advisory_unlock(42);
SELECT count(*) AS advisory_locks FROM pg_locks WHERE locktype = 'advisory';
```

## the one that outlives your transaction

a session-level lock doesn't belong to a transaction at all. take it inside BEGIN, roll back, and you still have it:

<Predict question="T1 runs BEGIN; SELECT pg_advisory_lock(7); ROLLBACK. then T2 runs SELECT pg_try_advisory_lock(7). what does T2 get?" options={["true: the rollback released it", "false", "an error"]} answer={1}>
```sql
/* T1 */ BEGIN;
/* T1 */ SELECT pg_advisory_lock(7);
/* T1 */ ROLLBACK;
/* T2 */ SELECT pg_try_advisory_lock(7);  -- ?
```
<Explain>
false. ROLLBACK undoes the transaction's changes and releases its transaction-level locks; a session-level advisory lock is neither. T1 holds lock 7 until it calls pg_advisory_unlock(7) or disconnects. use pg_advisory_xact_lock if you want the lock to follow the transaction.
</Explain>
</Predict>

the same thing in the browser's one session, both kinds at once:

```sql run
BEGIN;
SELECT pg_advisory_lock(7);
SELECT pg_advisory_xact_lock(8);
ROLLBACK;
SELECT objid AS key, mode FROM pg_locks
WHERE locktype = 'advisory' ORDER BY objid;
```

key 7 is still held, key 8 went with the transaction. session-level locks also stack: take one twice and you have to unlock it twice. and unlocking one you don't hold returns false, with a warning:

```sql run
SELECT pg_advisory_lock(42);
SELECT pg_advisory_lock(42);
SELECT pg_advisory_unlock(42);
SELECT count(*) AS still_held FROM pg_locks WHERE locktype = 'advisory';
SELECT pg_advisory_unlock(42);
SELECT pg_advisory_unlock(42);
```

## picking the number

the key is just a number, shared by the whole database. two features that both pick 42 will block each other and never know why. so make the key from a name: `hashtextextended('nightly-report', 0)` turns a string into a bigint, and the two-int form lets you put a feature number in the first half and a row id in the second (`pg_advisory_xact_lock(7, account_id)`: "only one payout per account at a time", without locking the account row itself).

```sql run
SELECT hashtextextended('nightly-report', 0) AS key,
       pg_try_advisory_lock(hashtextextended('nightly-report', 0)) AS got_it;
```

<Gotcha title="session locks and connection pools">
a session-level lock belongs to the database connection, not to your request. behind a pool, the connection outlives the request: forget the unlock (an exception, an early return) and the lock stays held by a pooled connection that some other request will get next, which can't take it. behind a pooler in transaction mode (pgbouncer's `pool_mode = transaction`), consecutive statements of one client can even land on different server connections, so the unlock may run on a connection that doesn't hold the lock and return false. prefer the `_xact` functions there: they can't outlive the transaction. ([connections and pooling](/learn/scale/connections-and-pooling).)
</Gotcha>

<Interview q="how would you make sure a scheduled job runs on only one of several app servers?">
use an advisory lock as a cluster-wide mutex: each server calls pg_try_advisory_lock with a key derived from the job's name; the one that gets true runs the job and then unlocks, the others get false and skip. pg_try_ doesn't wait, so a slow run doesn't pile up the others. if the whole job runs in one transaction, pg_try_advisory_xact_lock is safer, since COMMIT or ROLLBACK releases it no matter how the code exits; a session-level lock survives rollbacks and must be unlocked explicitly (or released when the connection closes). bonus point: advisory locks show up in pg_locks with locktype 'advisory', so a stuck job is visible as a held lock.
</Interview>

<Keylines>
- an advisory lock is a lock on a number. postgres enforces only that two can't hold it at once.
- pg_advisory_lock waits; pg_try_advisory_lock returns true or false at once.
- session-level locks survive COMMIT and ROLLBACK. they last until unlock or disconnect.
- _xact locks end with the transaction. prefer them behind connection pools.
- derive keys from names, and keep one key space for the whole database.
</Keylines>
