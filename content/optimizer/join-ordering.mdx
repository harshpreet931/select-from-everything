<InShort>
a join of n tables can be done in a huge number of orders: n! just for the left-deep ones. postgres finds the cheapest with **dynamic programming**: cheapest way to join every pair, then every set of three built from those, up to all n. that's exhaustive and exact, and it grows like 2ⁿ.

two settings keep it in check. **join_collapse_limit** and **from_collapse_limit** (8) stop the planner from reordering more than 8 items at once, and past **geqo_threshold** (12) items it switches to a **genetic** search that's fast and usually close.
</InShort>

## the picture

you know how the order you write JOINs in doesn't matter, except sometimes it does? the planner is free to reorder them, up to a point, and past that point it stops.

think of planning a road trip through four cities. you could try every order and price each, and with four that's 24 tours. with 12 it's 479 million. the smart way is to note the cheapest route between every pair of cities once, then build the cheapest three-city routes out of those, and so on. you never price a bad route twice. that's what postgres does with tables.

## n tables, n! orders

how many ways to join n tables? counting only left-deep trees (each join adds one table to what's built so far), it's n!: every order of the tables. bushy trees (two joins joined to each other) add more. postgres's dynamic programming instead works over **sets of tables**, and there are only 2ⁿ − 1 of them:

the important bit: a set's cheapest path is computed once and reused by every bigger set that contains it. that's what turns n! into something closer to 2ⁿ. it's also why the planner considers plans that start from customer 42 even though you wrote products first.

## the limits

```sql run
SELECT name, setting FROM pg_settings
WHERE name IN ('join_collapse_limit', 'from_collapse_limit', 'geqo', 'geqo_threshold')
ORDER BY name;
```

- **join_collapse_limit** (8): explicit `JOIN`s are flattened into one list to reorder only while the list stays at 8 items or fewer. past that, the joins are planned in groups, in the order written. at 1, every explicit JOIN is planned where you wrote it, which is how you'd force an order without hints ([steering the planner](/learn/optimizer/steering-the-planner)).
- **from_collapse_limit** (8): the same for subqueries in FROM being pulled up into their parent's list, and for comma-separated FROM lists.
- **geqo_threshold** (12): when a list to reorder has 12 or more items, dynamic programming is replaced by the genetic query optimizer.

`OUTER JOIN`s are reordered only where that's provably the same result ([outer joins](/learn/joins/outer-joins) has why), so a chain of LEFT JOINs often stays close to the written order anyway.

<Predict question="join_collapse_limit = 1. which FROM still gets reordered?" options={["a JOIN b JOIN c", "a, b, c with conditions in WHERE", "neither"]} answer={1}>
```sql
SET join_collapse_limit = 1;
```
<Explain>
the comma list. join_collapse_limit only governs explicit JOIN syntax; a comma-separated FROM is reordered up to from_collapse_limit. in the figure, the commas under limit 1 still get the cheap plan.
</Explain>
</Predict>

## the genetic optimizer

past 12 tables, postgres treats join orders like a population: random orders, scored by cost, the cheaper ones recombined for a number of generations. it's a heuristic: fast, and not guaranteed to find the best plan. it's deterministic for a given `geqo_seed` (0 by default), so the same query gets the same plan.

here's a chain of 10 to 14 small tables, joined with `join_collapse_limit` raised so nothing gets split, planned with the genetic optimizer and with the exhaustive search:

```sql run session=geqo
DO $$
BEGIN
  FOR i IN 1..14 LOOP
    EXECUTE format('CREATE TABLE t%s (id int PRIMARY KEY, next_id int, v int)', i);
    EXECUTE format('INSERT INTO t%s SELECT g, (g * 7) %% %s + 1, g %% (%s + 2) FROM generate_series(1, %s) AS g ORDER BY g', i, 100 * (15 - i), i, 100 * i);
    EXECUTE format('ANALYZE t%s', i);
  END LOOP;
END $$;
CREATE FUNCTION chain(n int) RETURNS text LANGUAGE sql AS $$
  SELECT 'SELECT count(*) FROM t1' || string_agg(format(' JOIN t%s ON t%s.id = t%s.next_id AND t%s.v < %s', i, i, i - 1, i, i % 4 + 1), '' ORDER BY i)
  FROM generate_series(2, n) AS i
$$;
CREATE FUNCTION plan_cost(q text) RETURNS numeric LANGUAGE plpgsql AS $$
DECLARE j json;
BEGIN
  EXECUTE 'EXPLAIN (FORMAT JSON) ' || q INTO j;
  RETURN (j->0->'Plan'->>'Total Cost')::numeric;
END $$;
SET join_collapse_limit = 20;
SELECT n, plan_cost(chain(n)) AS cost FROM generate_series(10, 14) AS n ORDER BY n;
SET geqo = off;
SELECT n, plan_cost(chain(n)) AS cost FROM generate_series(10, 14) AS n ORDER BY n;
```

worse plans in exchange for planning time: the exhaustive search over 14 tables can take long enough to matter on every execution. if a big join gets a bad plan, raising geqo_threshold (and the collapse limits) can help, and so can splitting the query so the planner sees smaller problems. measure planning time with EXPLAIN (ANALYZE, SUMMARY ON) when you try.

<Gotcha title="views count too">
a query that joins three views of five tables each is a 15-table join once the views are expanded and pulled up. join_collapse_limit and from_collapse_limit apply to the flattened list, so a query that looks small can be split into groups planned in written order, or handed to the genetic optimizer.
</Gotcha>

<Interview q="how does postgres pick a join order?">
by cost, with dynamic programming over sets of tables: the cheapest path for every single table, then for every pair connected by a join condition, then every set of three, up to the whole query, reusing each set's cheapest paths. it's exhaustive, so it finds the cheapest plan under its estimates, but grows exponentially. explicit JOINs are only reordered within join_collapse_limit items (8), FROM lists and pulled-up subqueries within from_collapse_limit (8), and at geqo_threshold (12) items it switches to a genetic algorithm. bonus point: join_collapse_limit = 1 makes postgres follow the written JOIN order, the closest thing to a join-order hint in core postgres.
</Interview>

<Keylines>
- n tables have n! left-deep join orders. postgres doesn't try them all.
- dynamic programming prices sets of tables level by level and reuses each set's cheapest path.
- explicit JOINs are reordered within join_collapse_limit (8), FROM lists within from_collapse_limit (8).
- at geqo_threshold (12) items, a genetic search takes over: faster, not always the best plan.
- join_collapse_limit = 1 follows the written JOIN order.
</Keylines>
