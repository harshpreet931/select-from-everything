<InShort>
with **data checksums** on, every page gets a 16-bit checksum when it's written to disk, and it's verified every time the page is read back. a mismatch is an error, "invalid page", instead of wrong data. they're **on by default since postgres 18**. a checksum only *detects*: it can't repair the page, it can't see corruption that happened in memory, and it can't tell an old page from a current one.
</InShort>

## the picture

you know how a disk that fails usually fails loudly, with an I/O error? the scary failures are the quiet ones: a firmware bug, a bad cable, a cosmic ray in a controller's cache, and a few bytes on a page change. the read succeeds. the data is wrong. nobody notices until a report doesn't add up.

think of a parcel with a seal (the checksum). the warehouse seals it when it ships (writes the page) and checks the seal when it arrives (reads it). a broken seal doesn't tell you what was in the box, and it can't put the contents back. it just stops you from signing for a box that was tampered with. and if someone swapped in last week's sealed box, the seal looks fine.

the lab engine has checksums on, like any cluster initdb'd by postgres 18. right after the dataset is loaded, the stored checksum matches what `page_checksum()` (pageinspect) computes:

```sql run db=lab session=ck
SHOW data_checksums;
SELECT checksum AS stored, page_checksum(get_raw_page('accounts', 0), 0) AS computed
FROM page_header(get_raw_page('accounts', 0));
```

change a row and look again. the page in shared buffers has changed, its header hasn't, and that's fine: nothing checks the checksum in memory. a checkpoint writes the page out with a fresh checksum on the copy it hands to the file; once the buffer is evicted and read back, the stored value matches again:

```sql run session=ck
UPDATE accounts SET balance = balance + 1 WHERE id = 1;
SELECT checksum AS stored, page_checksum(get_raw_page('accounts', 0), 0) AS computed
FROM page_header(get_raw_page('accounts', 0));
CHECKPOINT;
SELECT pg_buffercache_evict(bufferid) IS NOT NULL AS evicted FROM pg_buffercache
WHERE relfilenode = pg_relation_filenode('accounts') AND relforknumber = 0;
SELECT checksum AS stored, page_checksum(get_raw_page('accounts', 0), 0) AS computed
FROM page_header(get_raw_page('accounts', 0));
```

that's the whole value of checksums, in one comparison. `Alice` with a capital A is plausible data. if the byte had been in a balance, it would have been a plausible number. without checksums, postgres has no way to know the page isn't what it wrote. the server log on the checksum cluster has the details the client doesn't get:

```text
LOG:  page verification failed, calculated checksum 59722 but expected 60989
STATEMENT:  SELECT id, owner, balance FROM accounts ORDER BY id;
ERROR:  invalid page in block 0 of relation "base/5/16430"
```

`pg_checksums` checks a whole cluster offline (the server must be stopped). it found the same page before the restart:

```bash
$ pg_checksums --check -D $PGDATA
pg_checksums: error: checksum verification failed in file "$PGDATA/base/5/16430", block 0: calculated checksum E94A but block contains EE3D
Checksum operation completed
Files scanned:   954
Blocks scanned:  2926
Bad checksums:  1
```

(E94A and EE3D are 59722 and 60989 in hex: the same two numbers.) `pg_checksums --enable` turns checksums on for an existing cluster, also offline, by rewriting every page: on the other cluster it wrote all 2,926 blocks. there's no way to turn them on while the server runs.

## what a checksum can't catch

<Figure caption={<>what data checksums notice, and what slips past. the right column is why you still need backups and amcheck.</>}>
<Tree>{`
caught #live
    bits flipped on disk, in the controller, on the wire // any change to the 8 KB after the write
    a page written to the wrong place // the block number is part of the checksum
    a torn page // half old, half new rarely checksums right (and full-page writes repair it anyway)
not caught #dead
    corruption in memory, before the write // the checksum is computed over the bad bytes
    a lost write // last week's page, intact, still has a valid checksum
    bugs that write wrong but well-formed data // the page is exactly what postgres wrote
    damage on a cluster without checksums // turning them on later checksums the damage too
`}</Tree>
<Provenance drawn="from the postgres 18 docs on data checksums and the page checksum code (checksum_impl.h)" />
</Figure>

the checksum is 16 bits (an FNV-1a variant, folded), so a random corruption has roughly a 1 in 65,000 chance of slipping through. for index pages and anything else, `amcheck` checks structure (`bt_index_check`, `verify_heapam`), which catches the logical damage a checksum can't. `pg_stat_database.checksum_failures` counts failures per database, worth an alert.

the price is small but real. checksums mean a hint-bit change after a checkpoint has to be WAL-logged as a full page ([full-page writes](/learn/wal/full-page-writes), the `FPI_FOR_HINT` records), and every read and write computes 8 KB of hash. postgres turned them on by default in 18 because silent corruption is worse.

<Gotcha title="pg_upgrade needs matching checksum settings">
postgres 18's initdb turns checksums on, so a new 18 cluster won't accept a pg_upgrade from an old cluster that never had them: the settings must match. either `initdb --no-data-checksums` for the new cluster (the option 18 added for exactly this), or run `pg_checksums --enable` on the old one first, which means downtime proportional to its size. plan it before the upgrade window, not during.
</Gotcha>

<Interview q="what do data checksums protect against in postgres, and what don't they?">
each page gets a 16-bit checksum computed when it's written out and verified when it's read in, so corruption anywhere between the write and the next read (disk, controller, firmware, filesystem) raises "invalid page" instead of returning wrong data. they don't repair anything, they don't catch corruption that happened in memory before the write, they can't detect a lost write where an older but valid page comes back, and they can't catch logically wrong data postgres itself wrote. on by default since 18; on older clusters, pg_checksums --enable works offline. the side cost is WAL: with checksums, hint-bit changes after a checkpoint need full-page images. bonus point: pair them with amcheck for structural checks, and with backups and replicas, because detection is only useful if you have a good copy to go back to.
</Interview>

<Keylines>
- a checksum is computed when a page is written out and checked when it's read back.
- a mismatch raises "invalid page in block N". without checksums, the damage comes back as data.
- on by default since postgres 18. pg_checksums enables, disables or checks them, offline.
- detection only: no repair, no in-memory corruption, no lost writes.
- ignore_checksum_failure lets you read a damaged page for a rescue. it doesn't fix it.
</Keylines>
