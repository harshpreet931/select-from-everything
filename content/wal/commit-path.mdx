<InShort>
COMMIT writes a small **commit record** to the WAL, **flushes** the WAL up to it (XLogFlush, an fsync), marks the transaction committed in **pg_xact**, and only then says COMMIT. the flush is the expensive part, so backends that commit at the same moment share one: **group commit**. `synchronous_commit = off` skips waiting for the flush. it can lose the last few acknowledged commits in a crash, but never leaves the data half-applied.
</InShort>

## the picture

you know how COMMIT is the one statement that's slow even when it does nothing? `COMMIT` on a transaction that changed one row can take longer than the UPDATE did. that's because it's the only moment postgres has to wait for the disk.

think of a courier office. clerks write delivery slips all day (WAL records, in memory). a van takes everything written so far to the depot (a flush), and only when the van is back can the clerk tell the customer "it's on its way" (COMMIT returns). if five customers are waiting at once, one van trip serves all five (group commit). or you can tell customers "it's on its way" before the van leaves, and hope it doesn't crash on the way (`synchronous_commit = off`).

## watch the flush pointer

the browser engine has no WAL writer and no other sessions, so the flush pointer only moves when you make it:

```sql run db=lab session=commit
SELECT count(*) FROM accounts;
SELECT pg_current_wal_insert_lsn() AS inserted, pg_current_wal_flush_lsn() AS flushed;
UPDATE accounts SET balance = balance + 1 WHERE id = 1;
SELECT pg_current_wal_insert_lsn() AS inserted, pg_current_wal_flush_lsn() AS flushed;
```

before the UPDATE, the flushed position trails the inserted one (the first query's catalog reads wrote WAL, and nothing has committed since the dataset was loaded). the UPDATE runs in its own transaction, commits, and after it the two are equal: COMMIT flushed everything inserted so far, not just its own record. you can't flush the middle of a log.

now the same with `synchronous_commit = off`:

```sql run session=commit
SET synchronous_commit = off;
UPDATE accounts SET balance = balance + 1 WHERE id = 2;
SELECT pg_current_wal_insert_lsn() AS inserted, pg_current_wal_flush_lsn() AS flushed;
SELECT xmin, pg_xact_status(xmin::text::xid8) AS status FROM accounts WHERE id = 2;
```

COMMIT returned, the transaction is `committed` in pg_xact and visible to everyone, and its WAL is still not on disk. on a server, the WAL writer flushes it within moments. in the browser nobody does until the next synchronous commit. that window is the risk: if the server crashes inside it, a transaction whose client was told "committed" is simply gone after recovery. [crash recovery](/learn/wal/crash-recovery) has a capture of exactly that.

no. an abort record is written, but nothing waits for it to reach disk. losing it in a crash changes nothing: a transaction with no commit record counts as aborted after recovery anyway. only commits have to be durable.

## group commit

one client pays for one flush per commit. sixteen clients don't pay sixteen times: when a backend gets to XLogFlush, it flushes everything inserted so far, including other backends' commit records that arrived while the last flush was in progress. those backends find their record already on disk and return without flushing at all.

sixteen clients got 2,121 commits a second through a disk that does about 250 flushes, 8 commits per flush, with no setting changed. `commit_delay` (in microseconds, 0 by default) makes the flushing backend wait a little first, if at least `commit_siblings` (5) other transactions are active, so more commit records can pile into the same flush: about 12 per flush and 2,474 commits a second here. but on this mac's default `open_datasync`, where a "flush" doesn't reach the drive's media and costs tens of microseconds, the same 1 ms delay cut throughput from 85,831 to 12,355 commits a second. a delay only pays when a flush costs more than the delay. measure before you set it.

## synchronous_commit, all five levels

| level | COMMIT waits for | a crash of this server can lose | notes |
| --- | --- | --- | --- |
| `off` | nothing | the last few commits (up to 3x `wal_writer_delay`) | never inconsistent, just missing the tail |
| `local` | the local flush | nothing | ignores synchronous standbys |
| `remote_write` | local flush + the standby has written it (OS cache) | nothing | a standby crash plus its OS crash can lose it there |
| `on` (default) | local flush + the standby has flushed it | nothing | with no synchronous standby, same as local |
| `remote_apply` | local flush + the standby has replayed it | nothing | reads on the standby see the commit right away |

the three remote levels only mean something when `synchronous_standby_names` lists a standby ([streaming replication](/learn/wal/streaming-replication)). and it's per transaction: `SET LOCAL synchronous_commit = off` inside a transaction that logs a page view, and keep money on `on`.

<Gotcha title="synchronous_commit = off is not fsync = off">
they sound alike and are nothing alike. `synchronous_commit = off` can lose the last few hundred milliseconds of commits in a crash, and the database is still consistent: every transaction is either there or cleanly absent. `fsync = off` lets the operating system reorder and drop writes, so after a power cut the WAL and the pages can disagree in ways recovery can't fix, and you restore from backup. the first is a reasonable trade for some data. the second is for scratch clusters only.
</Gotcha>

<Deep title="how these were measured">
a bash script in the scratchpad started a throwaway postgres 18.6 cluster (Postgres.app's binaries, `initdb --no-locale`, unix socket only, `shared_buffers = 256MB`, autovacuum off), created `t (id bigserial PRIMARY KEY, v int)`, and ran `pgbench -n -f ins.sql -c N -j N -T 10` where ins.sql is `INSERT INTO t (v) VALUES (1);`. before each run it set synchronous_commit and commit_delay with ALTER SYSTEM and pg_reload_conf(), and reset pg_stat_io and pg_stat_database; after it, it read `sum(fsyncs)` and `sum(writes)` from pg_stat_io where `object = 'wal'`, and `xact_commit`. three runs per setting, medians shown.

macOS's default `wal_sync_method` is `open_datasync`, which doesn't make the drive flush its own cache, so a "flush" costs tens of microseconds (pg_test_fsync: 47 µs per 8 kB write) and one client did 23,373 synchronous commits a second. that's fast because it isn't fully durable against power loss. `fsync_writethrough` uses `F_FULLFSYNC`, which does flush it: 3,942 µs per write, which is the figure used above. a linux server with fdatasync on a datacenter SSD with power-loss protection usually lands in between. your numbers will differ; the shape won't.
</Deep>

<Interview q="what happens when you call COMMIT in postgres, and how would you make commits faster?">
the backend writes a commit record into the WAL buffers, then calls XLogFlush to write and fsync the WAL up to that record (unless another backend's flush already covered it), then marks the xid committed in pg_xact, releases its locks and returns. the fsync dominates. to go faster: batch more work per transaction; let concurrency do group commit (many backends committing together share one flush); use faster storage for pg_wal; consider commit_delay if flushes are slow and concurrency is high; and for data that can tolerate losing the last moment of commits, synchronous_commit = off per transaction, which can lose acknowledged commits in a crash but never corrupts. never fsync = off. bonus point: with a synchronous standby, the commit also waits for the standby, at the level synchronous_commit names.
</Interview>

<Keylines>
- COMMIT: append the commit record, flush the WAL up to it, mark pg_xact, release locks, return.
- the flush is the cost. on a disk that really flushes, about one per few milliseconds.
- group commit: concurrent commits share one flush. 8 per flush here with 16 clients, for free.
- synchronous_commit = off returns before the flush. a crash can lose the tail, never consistency.
- ROLLBACK doesn't wait for anything.
- commit_delay helps only when flushes are slow. measure.
</Keylines>
