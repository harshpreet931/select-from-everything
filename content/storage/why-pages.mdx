<InShort>
memory answers in about a tenth of a microsecond. an SSD answers a random read in tens of microseconds: on the machine this was measured on, hundreds of times slower. but most of an SSD's time goes on the request, not the bytes: reading 8 KB costs the same as 4 KB, and 64 KB only 1.6 times as much.

so databases never read a row. they read a fixed-size block, a **page** (8 KB in postgres), and every table and index is a file of them. ask for one row, and its whole page comes with it.
</InShort>

## the picture

you know how fetching one row by its id is fast, and reading a whole table is slow, even though both are just "reading the table"? the difference isn't the rows. it's how many trips to storage each one makes.

think of a warehouse across town. the drive is what costs you: half an hour there, half an hour back. once you're there, carrying out a box of books takes hardly longer than carrying out one. so nobody drives over for a single book. you bring the box, and if the next book you want happens to be in it, you already have it. the box is a page.

two gaps matter. memory against a random SSD read: 122 ns against 82 µs, about 670 times. and a random SSD read against reading the same SSD in order: 82 µs against 2.8 µs per 8 KB. storage loves big, sequential, predictable reads, and punishes small scattered ones. a database's whole storage layer is shaped around those two facts.

doubling from 4 KB to 8 KB is free. 64 KB, eight times the data, takes 1.6 times as long. that's the shape of every storage device: a large fixed cost per request (finding the data, the command round trip, on a hard disk the seek), and a small cost per byte after that. so the unit of I/O should be big enough that the fixed cost is shared by a lot of useful data, and small enough that a random lookup doesn't drag in megabytes it won't use. postgres picked 8 KB.

<Deep title="how these were measured">
two small C programs, compiled with `cc -O2`, run on an idle M4 Pro with 24 GB of RAM, macOS, the internal SSD. RAM: chase pointers through a random cycle over 1 GiB (each hop is one dependent load, so nothing can be prefetched), and `memcpy` 8 KB from random spots of the same buffer. OS cache: `pread` 8 KB at random aligned offsets of a 2 GiB file that was just written and read back. SSD: `pread` at random aligned offsets of a 4 GiB file opened with `F_NOCACHE` and `F_RDAHEAD` off, written the same way so it was never cached, 20,000 reads for the ladder and 5,000 per size for the sweep, median reported. three runs of the ladder agreed within 4%, including the random 8 KB SSD read, at 80.6, 82.0 and 82.1 µs. the size sweep, a separate program run separately, got 72 µs for the same read: the SSD's own mood varies that much between runs. treat them as one machine's numbers, not a law: a server SSD, a cloud volume and a laptop will all differ, but the ratios hold roughly everywhere.

```c
// the heart of the SSD measurement
int fd = open(path, O_RDONLY);
fcntl(fd, F_NOCACHE, 1);   // don't serve from or fill the OS cache
fcntl(fd, F_RDAHEAD, 0);   // no read-ahead
for (int i = 0; i < reps; i++) {
  double t0 = now();
  pread(fd, buf, 8192, (rnd() % blocks) * 8192);
  lat[i] = now() - t0;
}
// sort lat, report lat[reps / 2]
```
</Deep>

## so, pages

in postgres every table and index is a file cut into 8 KB pages, numbered from 0. a row lives on one page, and the page is the smallest thing that's ever read or written:

```sql run db=lab
SHOW block_size;
SELECT pg_relation_size('notes') AS bytes, pg_relation_size('notes') / 8192 AS pages,
       count(*) AS rows
FROM notes;
```

the lab's 400 notes are 5 pages: 40,960 bytes. so how much does reading one of them cost? pick a row:

<Explain>
5 and 2. the whole table is 5 pages, and a seq scan reads each once. the single row needs 2: the index's one leaf page (400 keys fit in a single page, so the leaf is also the root), then the heap page it points at. on a bigger table the index is taller and the lookup reads 3 or 4. either way, reading 400 rows cost two and a half times what reading one did.
</Explain>
</Predict>

```sql run db=lab
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF) SELECT * FROM notes;
```

```sql run db=lab
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF) SELECT * FROM notes WHERE id = 200;
```

each block starts from a cold copy, and the `Buffers:` line counts pages: `read=5` for all 400 rows, `read=2` for one. (`dirtied=5` is the scan setting [hint bits](/learn/mvcc/commit-log-and-hint-bits) on pages nobody had read since they were written, and the `Planning:` reads are the catalog and the index's metapage.) this is why the planner thinks in pages, not rows, and why a query that reads a few percent of a table through an index can lose to just reading the whole thing in order ([when postgres uses an index](/learn/indexes/index-or-scan)). and it's why everything in this part of the book, from [the layout of a page](/learn/storage/the-page) to [the cache in front of the disk](/learn/storage/buffer-pool), is about pages.

## why 8 KB, and not 4 or 16

8 KB is a compile-time choice in postgres (`--with-blocksize`), and almost nobody changes it. it sits between the sizes around it:

```sql run db=lab
SHOW block_size;
SHOW wal_block_size;
SHOW segment_size;
```

on this mac the SSD reports 4,096-byte blocks and the OS manages memory in 16 KB pages (`diskutil info` and `sysctl hw.pagesize` say so), so a postgres page is two device blocks and half an OS page. other engines pick differently: InnoDB's default page is 16 KB ([mysql 8.4 manual](https://dev.mysql.com/doc/refman/8.4/en/innodb-parameters.html#sysvar_innodb_page_size)), sqlite's is 4 KB since version 3.12.0 ([sqlite docs](https://www.sqlite.org/pragma.html#pragma_page_size)). bigger pages mean more rows per read and shallower indexes. smaller pages mean less waste when you only wanted one row, and less to write when one row changes. there's no free lunch, just a choice made decades ago that has held up.

<Gotcha title="the OS page cache is in the way, in a good way">
in the ladder, an 8 KB read from the OS page cache took 1 µs, 80 times faster than the SSD. postgres reads through that cache like any program, so a "read" in EXPLAIN is often a 1 µs memory copy, not an 80 µs trip to the SSD. it makes benchmarks lie: run a query twice and the second is fast because of a cache, not your index. measure cold and warm, and say which.
</Gotcha>

<Interview q="why do databases read and write in pages instead of rows?">
because storage has a large fixed cost per request and a small cost per byte. a random 8 KB read from an SSD costs about as much as a 4 KB one, and a hard disk's seek dwarfs the transfer entirely. moving fixed-size blocks amortizes that cost, lets the buffer cache and the OS manage memory in uniform units, and gives every row a stable physical address (page, slot). bonus point: it also explains why access patterns matter more than row counts: one row through an index costs several page reads, and a sequential scan reads rows by the hundred per page, in order, which storage is much faster at.
</Interview>
