<InShort>
**INSERT** adds rows: name the columns, give the values, one row or many per statement. a column you leave out gets its **DEFAULT**, and a column with no default gets NULL. `INSERT ... SELECT` fills a table from a query.

ids come from a **sequence**, and a sequence never gives a number back: a failed or rolled-back insert leaves a **gap**.
</InShort>

## the picture

you know how a spreadsheet lets you type into any empty cell, anywhere? a table doesn't. it has a fixed set of columns with types and rules, and the only way in is a whole row at a time.

think of a form at a counter. every box on the form is a column. some boxes are pre-filled (the defaults), some you must fill (NOT NULL), and the clerk stamps the number in the corner herself (the identity column). hand in a form with a required box empty and the whole form comes back, nothing filed.

## your first table

before you can insert, there has to be somewhere to insert into. this is the table from the figure:

```sql run session=teas title="teas.sql"
CREATE TABLE teas (
  id     int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name   text NOT NULL,
  origin text,
  grams  int NOT NULL DEFAULT 100
);
```

four columns, read left to right: a name, a type, then the rules. `id` numbers itself and is the [primary key](/learn/design/keys). `name` has to be there. `origin` may be NULL. `grams` falls back to 100. (the rules themselves are a chapter of their own: [NOT NULL, CHECK and UNIQUE](/learn/design/constraints).)

now one row. list the columns you're filling, then the values in the same order:

```sql run session=teas
INSERT INTO teas (name, origin, grams) VALUES ('assam', 'india', 250);
SELECT * FROM teas ORDER BY id;
```

`INSERT 0 1` is the command tag: 1 row inserted. the 0 is a leftover. it used to be the inserted row's oid, and tables haven't had oids since postgres 12, so it's always 0 now.

## many rows, and defaults

one VALUES list can hold as many rows as you like, separated by commas. it's one statement, one round trip, and all or nothing:

```sql run session=teas
INSERT INTO teas (name, origin) VALUES
  ('sencha', 'japan'),
  ('darjeeling', 'india'),
  ('rooibos', 'south africa');
SELECT * FROM teas ORDER BY id;
```

nobody said `grams`, so all three got 100. a column you leave out of the list gets its default, and a column without a default declared gets NULL. you can also ask for the default by name, with the keyword `DEFAULT` in the VALUES:

```sql run session=teas
INSERT INTO teas (name, origin, grams) VALUES ('house blend', DEFAULT, DEFAULT);
SELECT * FROM teas WHERE name = 'house blend';
```

`origin` has no default, so DEFAULT means NULL there. and `NOT NULL` is the box you must fill:

```sql run session=teas expect=error
INSERT INTO teas (origin) VALUES ('china');
```

the error even shows the row it refused: `(6, null, china, 100)`. look at that 6. the id was already taken from the sequence before the NOT NULL check failed.

<Gotcha title="INSERT without a column list">
you can skip the column list and give a value for every column, in table order: `INSERT INTO teas VALUES (DEFAULT, 'genmaicha', 'japan', 80)`. it works today. the day someone adds a column, or a migration creates the columns in a different order on another server, it either fails or quietly puts a number in the wrong box. name your columns. it costs one line.
</Gotcha>

## the numbers have gaps

<Predict options={["6", "7", "8"]} answer={2}>
```sql
-- the last id handed out was 5 (house blend). then the
-- insert without a name failed, and then:
BEGIN;
INSERT INTO teas (name, origin, grams) VALUES ('pu-erh', 'china', 357);
ROLLBACK;
INSERT INTO teas (name, origin, grams) VALUES ('oolong', 'taiwan', 50);
-- what id does oolong get?
```
<Explain>
8. the failed insert took 6, pu-erh took 7, and neither number comes back. a sequence hands out numbers outside of any transaction, so that two sessions inserting at once never wait for each other just to get an id. the price is that rollbacks and errors leave holes.
</Explain>
</Predict>

<Figure wide caption={<>step through. pu-erh is real inside the transaction, then ROLLBACK strikes it out. the next row gets <C k="live">8</C>, not 6: 6 and 7 are gone for good.</>}>
<TableSteps frames={gap} table="teas" file="teas.sql" trace={source} />
</Figure>

here it is for real. the insert that failed already ran, two blocks up (this page runs a session's blocks in order), so this picks up right after it:

```sql run session=teas
BEGIN;
INSERT INTO teas (name, origin, grams) VALUES ('pu-erh', 'china', 357);
ROLLBACK;
INSERT INTO teas (name, origin, grams) VALUES ('oolong', 'taiwan', 50);
SELECT id, name FROM teas ORDER BY id;
```

ids are for telling rows apart, not for counting them. if you need "the 7th order this year" without holes, that's a number you compute (`row_number()`), not one you store. and if a gap in an id upsets a report, the report is wrong, not the id.

## where ids come from

`GENERATED ALWAYS AS IDENTITY` is the [standard](/learn/start/sql-and-its-dialects) spelling (SQL:2003), and postgres has had it since 10. older code uses `serial`, a postgres shorthand that creates a sequence and sets the column's default to `nextval(...)`. the difference shows up the first time someone types an id by hand:

<Figure wide caption={<>switch the kind of id column. the same two inserts: one with an id typed by hand, one without. GENERATED ALWAYS refuses the first. the other two accept it, and the sequence, which doesn't know about the 1, hands out 1 next.</>}>
<RunPick
  options={[{ key: "id column", values: ["GENERATED ALWAYS", "GENERATED BY DEFAULT", "serial"] }]}
  runs={kinds}
  hot={["GENERATED ALWAYS AS IDENTITY", "GENERATED BY DEFAULT AS IDENTITY", "serial"]}
  file="kinds.sql"
  trace={source}
/>
</Figure>

GENERATED ALWAYS catches the mistake when it's made. BY DEFAULT and serial catch it later, on somebody else's insert, as a duplicate key. (when you really do need to load ids by hand, say in a migration, `OVERRIDING SYSTEM VALUE` gets past ALWAYS, and then you move the sequence on with `setval`.)

this isn't hypothetical. shop's tables use BY DEFAULT, and customers go up to 2000. type in the next id yourself, and the next normal signup collides with you:

```sql run db=shop expect=error
INSERT INTO customers (id, name, country, created_at)
VALUES (2001, 'Typed By Hand', 'GB', '2026-05-01 10:00+00');

INSERT INTO customers (name, country, created_at)
VALUES ('Next Signup', 'GB', '2026-05-01 10:05+00');
```

[identity columns and uuids](/learn/types/identity-and-uuids) has the rest: why serial is legacy, and keys that don't need a sequence at all.

## INSERT ... SELECT

VALUES is one way to say "these rows". a query is the other. anything a SELECT returns can go straight into a table, as long as the columns line up. here's a table of shop's ten best customers, filled from a join in one statement:

```sql run db=shop session=vip
CREATE TABLE vip (
  customer_id int PRIMARY KEY REFERENCES customers,
  spent       numeric(12,2) NOT NULL
);

INSERT INTO vip (customer_id, spent)
SELECT o.customer_id, sum(oi.qty * oi.unit_price)
FROM orders AS o
JOIN order_items AS oi ON oi.order_id = o.id
WHERE o.status <> 'cancelled'
GROUP BY o.customer_id
ORDER BY sum(oi.qty * oi.unit_price) DESC, o.customer_id
LIMIT 10;
```

`INSERT 0 10`. the rows never left the database: no client fetched them and sent them back. that's why INSERT ... SELECT is the fast way to copy, reshape or archive data, and why a [bulk load](/learn/writes/copy-and-bulk-loads) usually ends with one.

```sql run session=vip
SELECT v.customer_id, c.name, v.spent
FROM vip AS v JOIN customers AS c ON c.id = v.customer_id
ORDER BY v.spent DESC, v.customer_id;
```

if the table doesn't exist yet, `CREATE TABLE vip AS SELECT ...` makes it and fills it in one go, with the columns the query returns (and no primary key, no constraints, no defaults: you add those after).

<Deep title="what one INSERT does underneath">
an INSERT finds a page with room for the row (the [free space map](/learn/storage/fsm-and-vm) knows), writes the row there with your transaction's id stamped in its header as xmin, adds an entry to every index on the table, and logs all of it to the [WAL](/learn/wal/write-ahead-rule) before COMMIT returns. the row exists on the page from the moment it's written; whether anyone else can see it depends on whether your transaction committed. [one INSERT, all the way down](/learn/deep-dives/one-insert-all-the-way-down) follows a single row through every one of those steps.
</Deep>

<Interview q="why are there gaps in my id column?">
because sequences are non-transactional on purpose. `nextval` hands out a number immediately and never takes it back, so concurrent inserts don't serialize on the counter. a rolled-back transaction, a failed insert (a constraint violation after nextval ran), an `INSERT ... ON CONFLICT` that took the update path, and the numbers a session cached but never used all leave holes. bonus point: never use ids to count rows or to order events across sessions; two transactions can commit in the opposite order to their ids.
</Interview>

<Keylines>
- INSERT adds whole rows: name the columns, then give the values.
- a column you leave out gets its DEFAULT, or NULL if it has none.
- one statement is all or nothing, even with a thousand rows in VALUES.
- INSERT ... SELECT fills a table from a query without the rows ever leaving the database.
- prefer GENERATED ALWAYS AS IDENTITY over serial, and expect gaps in the ids.
</Keylines>
