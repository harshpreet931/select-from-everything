<InShort>
**sharding** splits one table's rows across several independent databases, by a **shard key**. a query that names the key goes to one shard; a query that doesn't goes to all of them and gets merged. the key decides everything: an even spread of load (or a **hot shard**), which joins stay local, and how painful it is to add a machine later.
</InShort>

## the picture

you know how [partitioning](/learn/scale/partitioning) splits a table into pieces on one server? sharding is the same split with each piece on its own server, so the pieces stop sharing a CPU, a disk and a WAL. that's how writes scale past one machine, and it's also where every query starts needing a map.

think of a library that outgrew its building and moved into four branches (the shards). books are shelved by the author's surname (the shard key). ask for one author, and you know which branch to call. ask "every book published in 1999" and you're calling all four.

## picking a shard key

a good shard key is one that almost every query includes, that spreads both data and traffic, and that keeps rows queried together on the same shard. three common shapes:

- **hash of an id**: even data, no range queries across shards, and every user's rows together. what most systems default to.
- **range of an id or a name**: neighbours stay together, so range scans hit one shard. skew lands wherever the busy ranges are.
- **range of time**: wonderful for retention, terrible for writes. every insert goes to the newest shard.

the events dataset makes the skew real. hashing spreads users evenly, but users aren't equally busy:

```sql run db=events
SELECT ((hashint4(user_id) % 4) + 4) % 4 AS shard,
       count(DISTINCT user_id) AS users,
       count(*) AS events
FROM events
GROUP BY 1
ORDER BY 1;
```

```sql run db=events
SELECT user_id, count(*) AS events, round(100.0 * count(*) / sum(count(*)) OVER (), 1) AS pct
FROM events
GROUP BY user_id
ORDER BY events DESC, user_id
LIMIT 3;
```

one user owns more than 4% of all events. no hash can split one key across shards, so that user's shard carries all of it. a **hot key** like that (a celebrity account, a big tenant) needs special handling: its own shard, or a key that splits it (user plus day).

## joins across shards

a join is cheap when both sides live on the same shard. so sharded schemas get designed around it:

<Figure wide caption={<>where a join can run, depending on how its two tables are placed. hover a stage.</>}>

  { label: "repartition", sub: "move rows to match", note: "different keys on each side: rows are reshuffled over the network so matching keys meet. correct, and expensive." },

]} />
</Figure>

the same goes for constraints. a unique index or a foreign key is enforced inside one database; across shards, uniqueness only holds when the key includes the shard key (exactly the [partitioning](/learn/scale/partitioning) rule, for the same reason), and a transaction that writes to two shards needs [two-phase commit](/learn/scale/two-phase-commit) to be atomic.

## resharding

shards fill up, and you add one. with `hash mod n`, changing n changes almost every key's shard: going from 4 to 5 moves about 4 keys in 5. so real systems don't map keys to shards directly. they hash into a fixed, larger number of slots (or ranges, or a consistent-hashing ring) and move whole slots between machines, so adding a shard moves only its fair share. try both maps in the figure. the move itself is a copy plus catching up on changes made during the copy, often with [logical replication](/learn/wal/logical-replication), then a short pause to switch the map.

<Gotcha title="shard last">
sharding turns every query, every constraint and every migration into a distributed problem. before it: a bigger machine, [read replicas](/learn/scale/read-replicas) for reads, [partitioning](/learn/scale/partitioning) for retention, [pooling](/learn/scale/connections-and-pooling), and fixing the queries ([finding slow queries](/learn/optimizer/finding-slow-queries)). when it's truly needed, systems that do it for you (citus as a postgres extension, or the [distributed SQL](/learn/scale/distributed-sql) databases) save you writing the router, the rebalancer and the cross-shard planner yourself.
</Gotcha>

<Interview q="how would you choose a shard key?">
pick the column nearly every query filters on, that spreads both data and traffic evenly, and that keeps rows queried together on one shard (tenant_id for a SaaS app, user_id for a social app). avoid monotonically increasing keys like timestamps with range sharding, which send every insert to one shard. watch for hot keys that no hash can split. bonus point: hash into many fixed slots instead of mod n, so adding a shard moves only a small share of the data.
</Interview>

<Keylines>
- sharding = partitions on separate machines, chosen by a shard key.
- queries with the key hit one shard; without it, all of them (scatter, gather).
- hash spreads keys, not load: hot keys stay hot.
- co-locate tables that join; copy small reference tables everywhere.
- map keys to many slots, not mod n, so resharding moves little.
</Keylines>
