<InShort>
a query goes through five stages. the **parser** checks the grammar and builds a tree of words. the **analyzer** looks every name up in the catalog and turns it into numbers. the **rewriter** expands views (and rules). the **planner** picks the cheapest way to run it. the **executor** runs that plan, one row at a time.

each stage catches its own kind of mistake, which is why the same typo gives different errors depending on where it is.
</InShort>

## the picture

you know how a typo in a keyword says "syntax error", a typo in a table name says "does not exist", and a division by zero only fails once rows show up? three different errors, from three different places.

think of a letter going through a post office. the first desk only checks that it looks like a letter: stamp, address in the right place (the parser). the next looks the address up and writes the postcode on it (the analyzer). the next notices it's addressed to a PO box and rewrites it to the real street (the rewriter, expanding a view). the next picks the route (the planner). and the van drives it (the executor).

the numbers in those trees are oids from the catalog ([the system catalog](/learn/execution/system-catalog) has how to read them back), and you can ask what the two operators are:

```sql run db=shop
SELECT oid, oprname, oprleft::regtype AS left_type, oprright::regtype AS right_type
FROM pg_operator
WHERE oid IN (96, 98)
ORDER BY oid;
```

## the parser knows grammar, not tables

the parser has a list of keywords, and how reserved each one is:

```sql run db=shop
SELECT word, catdesc
FROM pg_get_keywords()
WHERE word IN ('select', 'from', 'where', 'name', 'form')
ORDER BY word;
```

`name` is unreserved, which is why customers can have a column called that. `form` isn't a keyword at all, so `SELECT name FORM customers` doesn't fail at FORM: an identifier after an expression is a column alias (AS is optional), and the grammar only gets stuck one word later. pick a mistake, see who catches it:

## the rewriter, and views

a view is stored as a rule in `pg_rewrite`: "a SELECT from this view is really this query". the rewriter applies it before the planner ever sees the query:

```sql run db=shop
CREATE VIEW londoners AS SELECT id, name FROM customers WHERE city = 'London';

SELECT rulename, ev_type, is_instead
FROM pg_rewrite
WHERE ev_class = 'londoners'::regclass;

EXPLAIN (COSTS OFF) SELECT name FROM londoners WHERE id = 42;
```

one rule, `_RETURN`, for SELECT (`ev_type` 1), INSTEAD. and the plan never mentions londoners: the view's query was spliced in, flattened, and its WHERE merged with yours, so customers_pkey can be used for `id = 42`. a view costs nothing at run time; it's a query you didn't have to type ([views](/learn/design/views)).

## planning and running

the planner is the [optimizer part](/learn/optimizer/cost-model) of this book: it generates candidate plans, estimates their costs from statistics, and keeps the cheapest. the executor is [the iterator model](/learn/execution/iterator-model): the plan as a tree of nodes, each answering "next row, please?".

the line between them is where prepared statements live. `PREPARE` runs the parser, analyzer and rewriter once and keeps the result; each `EXECUTE` plans (or reuses a plan) and runs it. which plans get reused is [generic plans](/learn/optimizer/generic-plans).

<Gotcha title="the planner can see constants, not values from a later stage">
the planner works before any row exists. it can fold `2 + 2` into 4 and use the constant 42 against statistics, but it can't know what `now()` or a parameter will be at run time, and it can't see inside a function's result. that's why an error that depends on a row (like the division by zero above) only shows up in the executor, and why a query can plan fine and still fail halfway through.
</Gotcha>

<Interview q="what happens when postgres receives a query?">
the parser checks the grammar and builds a parse tree. the analyzer resolves names against the catalog (tables, columns, types, operators, functions) and produces a query tree full of oids. the rewriter applies rules from pg_rewrite, which is how views get expanded into their defining query. the planner generates candidate plans, estimates their costs and keeps the cheapest. the executor runs the plan as a pull-based tree of operators and streams rows to the client. bonus points: syntax errors come from the parser, "does not exist" from the analyzer, and PREPARE caches everything up to the rewriter.
</Interview>

<Keylines>
- parser: grammar only. it has never heard of your tables.
- analyzer: names become oids from the catalog; "does not exist" comes from here.
- rewriter: views are rules in pg_rewrite, spliced in as subqueries.
- planner: picks the cheapest plan. executor: runs it, pulling rows up the tree.
- each stage catches its own mistakes, so the error tells you how far the query got.
</Keylines>
