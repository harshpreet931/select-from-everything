<InShort>
an **identity column** (`GENERATED ALWAYS AS IDENTITY`) is the standard way to number rows: a sequence behind the column, owned by it. `serial` is the older postgres shorthand for the same thing, with looser rules.

a **uuid** is a 128-bit id you can make anywhere, no sequence needed. random ones (version 4) scatter inserts across an index; **uuidv7()**, new in postgres 18, starts with a timestamp, so new keys sort last.
</InShort>

## the picture

you know how a deli hands out paper tickets from a dispenser? the dispenser is a sequence: it gives out the next number, never the same one twice, never takes one back. that's an identity column. a uuid is everyone printing their own ticket, with a number so long that two people never print the same one.

the difference shows up in the index. tickets from a dispenser always go at the end of the line. self-printed random tickets go wherever their number falls, which is anywhere. uuidv7 puts the time first, so self-printed tickets line up too.

## identity columns

[INSERT](/learn/writes/insert) already showed the three kinds of id column side by side and the gap a rollback leaves; this is the rest. an identity column is backed by an ordinary sequence, which postgres creates, names and ties to the column:

```sql run
CREATE TABLE teas (id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY, name text NOT NULL);
SELECT pg_get_serial_sequence('teas', 'id') AS sequence;
SELECT data_type, start_value, increment_by, max_value FROM pg_sequences WHERE sequencename = 'teas_id_seq';
```

`ALWAYS` means postgres refuses a hand-typed id, on INSERT and on UPDATE:

```sql run expect=error
CREATE TABLE teas (id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY, name text NOT NULL);
INSERT INTO teas (id, name) VALUES (10, 'oolong');
```

the escape hatch is `OVERRIDING SYSTEM VALUE`, for migrations and restores. it gets the row in, and leaves the sequence behind:

<Figure caption={<>five statements on one table, the sequence's <code>last_value</code> beside every row. step through: the hand-typed 3 goes in, the sequence still says 2, the next normal insert <C k="dead">collides</C>, and <code>setval</code> puts things right.</>}>
<RunPick options={[{ key: "after", values: ["two inserts", "OVERRIDING 3", "next insert", "setval", "insert again"] }]} runs={seq} file="teas.sql" trace={source} />
</Figure>

so every bulk load with explicit ids ends with a `setval(pg_get_serial_sequence(...), max(id))`. (`GENERATED BY DEFAULT` accepts the typed id without the OVERRIDING clause, and has exactly the same collision waiting.)

why not `serial`? it's postgres's older shorthand, not in the standard: it creates the same kind of sequence and sets the column's `DEFAULT nextval(...)`. so it behaves like BY DEFAULT (nothing stops a typed id), the sequence is a loose object you can see in the column default and change by accident, and dropping or copying the default doesn't drag the sequence along. identity is standard SQL <Since std="SQL:2003" />, and the sequence belongs to the column itself. use `bigint` for the column unless you're sure: an `integer` sequence stops at 2,147,483,647 ([integers](/learn/types/numbers)).

## uuids

a `uuid` is 16 bytes, printed as 36 characters. store it as `uuid`, not text, which is more than twice the size:

```sql run
SELECT pg_column_size('019a2b64-7f20-7b3c-9a1d-4e5f60718293'::uuid) AS as_uuid,
       pg_column_size('019a2b64-7f20-7b3c-9a1d-4e5f60718293'::text) AS as_text;
```

two ways to make one in postgres 18. `gen_random_uuid()` (or `uuidv4()`) makes a random version 4, and `uuidv7()` <Since v={18} /> makes a time-ordered version 7. their values change every run, so this page compares their *order*, not their digits:

```sql run volatile
WITH made AS (
  SELECT i, uuidv7() AS v7, gen_random_uuid() AS v4
  FROM generate_series(1, 1000) AS i
)
SELECT bool_and(v7 > prev_v7) AS v7_always_increasing,
       bool_and(v4 > prev_v4) AS v4_always_increasing
FROM (
  SELECT v7, v4, lag(v7) OVER (ORDER BY i) AS prev_v7, lag(v4) OVER (ORDER BY i) AS prev_v4
  FROM made
) AS pairs
WHERE prev_v7 IS NOT NULL;
```

all thousand uuidv7 values are bigger than the one before; the random ones aren't (each pair is a coin toss). a uuidv7 also tells you when it was made, which a v4 can't:

```sql run volatile
SET TimeZone = 'UTC';
SELECT uuid_extract_version(uuidv7()) AS v7, uuid_extract_version(gen_random_uuid()) AS v4,
       uuid_extract_timestamp(uuidv7()) > now() - interval '1 minute' AS v7_time_is_now,
       uuid_extract_timestamp(gen_random_uuid()) IS NULL AS v4_has_no_time;
```

<Explain>
a b-tree keeps keys in order, so a new key goes on the leaf page where it sorts. time-ordered keys (uuidv7, a sequence) always sort last, so a burst of inserts lands on the same last page or two, which stays in memory. random keys land anywhere, so the last 1,000 inserts touched every leaf in the index.
</Explain>
</Predict>

92 leaf pages for random keys against 77 for uuidv7: a random insert splits a page in the middle, leaving two half-full pages, where an append fills the last page and starts a new one. and the last 1,000 random inserts touched all 92 leaves, against 5 for uuidv7 and 4 for bigint. on a table bigger than memory, "every leaf" means reads from disk and more [WAL](/learn/wal/full-page-writes) per insert. (the uuid tree has more pages than bigint's 55 because each key is 16 bytes, not 8.) [b-trees, page by page](/learn/index-internals/nbtree-pages) and [page splits](/learn/index-internals/page-splits) show the mechanics.

<Gotcha title="uuidv7 puts a timestamp in your public ids">
anyone who sees a version 7 id can read when the row was created, to the millisecond. for most ids that's harmless, for some (a user id that leaks a signup date) it isn't. version 4 keeps nothing but randomness, and a bigint key with a separate random public id is the third option.
</Gotcha>

<Interview q="bigint identity or uuid for a primary key?">
a bigint identity is 8 bytes, ordered, fast, and needs the database to hand out every id. a uuid is 16 bytes and can be generated anywhere (clients, other services, offline), which matters for merging data or hiding row counts. random v4 uuids hurt the index: inserts land on random leaf pages, so a large index stops fitting in memory and splits leave pages half empty. uuidv7 (postgres 18) starts with a millisecond timestamp, so inserts append like a sequence. bonus point: after loading rows with OVERRIDING SYSTEM VALUE, setval the sequence or the next insert collides.
</Interview>

<Keylines>
- GENERATED ALWAYS AS IDENTITY is the standard id column; serial is the older, looser shorthand.
- OVERRIDING SYSTEM VALUE leaves the sequence behind: setval afterwards.
- pg_get_serial_sequence names the sequence behind an identity or serial column.
- store uuids as uuid (16 bytes), never as text.
- random uuids scatter inserts across the index; uuidv7 keys sort by time and append.
</Keylines>
