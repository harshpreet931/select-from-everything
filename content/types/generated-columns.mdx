<InShort>
a **generated column** is computed from other columns of the same row, and you can never write to it. **STORED** computes it on INSERT and UPDATE and keeps it on disk. **VIRTUAL** computes it every time it's read and stores nothing. postgres 18 added virtual generated columns, and made them the **default**.

the expression must be immutable and see only its own row. you can index a stored one; for a virtual one, you index its expression.
</InShort>

## the picture

you know how a spreadsheet has cells with formulas, `=B2*C2`, that you never type into? a generated column is that cell. the only question is when the formula runs: when the row is written, with the answer saved in the cell (stored), or every time someone looks at it (virtual).

think of a receipt. a stored total is printed at the till; reading it is free, and it takes ink. a virtual total is one you add up in your head each time you look, no ink, a little arithmetic.

## STORED, VIRTUAL, and the 18 default

before postgres 18, `STORED` was required. since 18 <Since v={18} />, VIRTUAL exists and is what you get if you don't say:

```sql run
CREATE TABLE items (
  qty        int NOT NULL,
  unit_price numeric(10,2) NOT NULL,
  total      numeric GENERATED ALWAYS AS (qty * unit_price)
);
SELECT attname, attgenerated FROM pg_attribute WHERE attrelid = 'items'::regclass AND attnum > 0 ORDER BY attnum;
INSERT INTO items (qty, unit_price) VALUES (3, 2.50) RETURNING total;
```

`v` in the catalog: virtual. either way the column is read-only. postgres computes it, and refuses a value from you (`DEFAULT` is the one thing you may write):

```sql run expect=error
CREATE TABLE items (qty int, unit_price numeric(10,2), total numeric GENERATED ALWAYS AS (qty * unit_price));
INSERT INTO items (qty, unit_price, total) VALUES (3, 2.50, 99);
```

the difference you'll feel first is adding one to a big table. a virtual column is a catalog change; a stored one rewrites every row:

<Figure caption={<>the events table (25,000 rows) before and after adding each kind of column. pick one. VIRTUAL keeps the same file and size; STORED writes a new file, and it's bigger.</>}>
<RunPick options={[{ key: "events", values: ["before", "ADD ... VIRTUAL", "ADD ... STORED"] }]} runs={alters} file="alter.sql" trace={source} />
</Figure>

(a rewrite also takes a lock that blocks reads and writes for as long as it runs. on a big table that's the outage.) so which one?

- **virtual** when the expression is cheap and the column is read less than the table is written: no disk, no rewrite to add it, and `ALTER COLUMN ... SET EXPRESSION` is a catalog change too.
- **stored** when the expression is expensive, or you need to index it, put a UNIQUE or foreign key on it, or build extended statistics on it. a virtual column can't have any of those.

## what the expression may do

a generated column is a function of its row and nothing else, forever. so the expression must be **immutable** (same input, same answer, always) and can only see the row's own columns:

<Figure wide caption={<>six things postgres refuses, each a real error. pick one. the first two aren't immutable: now() changes, and timestamptz to text depends on the session's TimeZone.</>}>
<RunPick options={[{ key: "uses", values: ["now()", "a::text", "another generated column", "a subquery", "your own function", "CREATE INDEX"] }]} runs={refused} file="refused.sql" trace={source} />
</Figure>

<Predict options={["it works", "an error", "it works only if STORED"]} answer={1}>
```sql
CREATE TABLE signups (
  at  timestamptz,
  day date GENERATED ALWAYS AS (at::date) STORED
);
```
<Explain>
an error: generation expression is not immutable. the day an instant falls on depends on the session's TimeZone ([timestamptz](/learn/types/timestamptz)), so `at::date` could give two answers for one row. name the zone and it becomes immutable: `(at AT TIME ZONE 'UTC')::date`.
</Explain>
</Predict>

```sql run
CREATE TABLE signups (
  at  timestamptz,
  day date GENERATED ALWAYS AS ((at AT TIME ZONE 'UTC')::date) STORED
);
INSERT INTO signups (at) VALUES ('2026-03-29 01:30+00') RETURNING day;
```

the user-defined-function rule is specific to virtual columns in 18 (the error says "not yet supported"). a stored column may call an immutable function you wrote, and it's on you that it really is immutable: change the function, and the stored values don't change with it.

## indexing a generated column

a stored generated column is an ordinary column on disk, so it takes ordinary indexes. a virtual one has nothing on disk to index, and postgres 18 says so. but a virtual column is expanded into its expression before planning, so an [expression index](/learn/indexes/partial-and-expression) on the same expression serves it:

```sql run db=events
ALTER TABLE events ADD COLUMN page text GENERATED ALWAYS AS (props ->> 'page');
CREATE INDEX events_page ON events ((props ->> 'page'));
ANALYZE events;
EXPLAIN (COSTS OFF) SELECT count(*) FROM events WHERE page = '/p/17';
```

the plan never mentions `page`. it shows the expression, and the index on it:

<Figure caption={<>EXPLAIN ANALYZE of a count on the virtual column. the bitmap index scan uses the expression index on <code>props -&gt;&gt; 'page'</code> and finds the 129 matching events.</>}>
<PlanTree plan={plan} show={["actual"]} provenance={<Provenance trace={source} />} />
</Figure>

that's the jsonb pattern from [json and jsonb](/learn/types/jsonb): keep the document, name the key you query with a virtual column, and index its expression. promote it to STORED when you need a constraint on it.

<Gotcha title="generated is not the same as DEFAULT">
a DEFAULT is computed once, at insert, and then it's an ordinary column you can overwrite. a generated column is recomputed whenever its inputs change and can't be overwritten. `created_at timestamptz DEFAULT now()` is a default (and now() couldn't be generated anyway). `total GENERATED ALWAYS AS (qty * unit_price)` stays right after every UPDATE of qty.
</Gotcha>

<Docs href="https://www.postgresql.org/docs/18/ddl-generated-columns.html" title="generated columns">the full list of restrictions for both kinds, including partitioning, inheritance and what logical replication does with each. the 18 release notes describe the switch to virtual as the default.</Docs>

<Interview q="stored or virtual generated column?">
virtual (the default since postgres 18) computes the value on read: no storage, no table rewrite to add it, but it can't be indexed, made UNIQUE, referenced by a foreign key, or use your own functions. stored computes it on write and keeps it on disk, so it can be indexed and constrained, at the cost of space and a full rewrite when you add it to an existing table. either kind needs an immutable expression over the same row. bonus point: you can still index a virtual column's expression, and queries on the column will use it.
</Interview>

<Keylines>
- a generated column is computed from its own row, and you can't write to it.
- STORED keeps the value on disk; VIRTUAL computes it on read. since 18, virtual is the default.
- adding a virtual column is a catalog change; adding a stored one rewrites the table.
- the expression must be immutable and see only the row; virtual ones can't call your functions.
- index a stored one directly, or a virtual one's expression.
</Keylines>
