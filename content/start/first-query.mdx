<InShort>
a query is a question, and the answer is always a table. `SELECT` says which columns you want, `FROM` says which table, `WHERE` (optional) says which rows, and a **semicolon** ends it.

you describe **what** you want. postgres decides **how** to get it.
</InShort>

## the picture

you know how in most programming languages you tell the computer every step: open this, loop over that, if this then that? SQL doesn't work that way, and it's the first thing that feels strange.

think of ordering at a restaurant. the menu is the schema (what tables and columns exist). your order is the query ("the soup, no onions"). the kitchen is the planner and executor: they decide which pot, which burner, in what order. you never walk into the kitchen. you get a plate, and the plate is always the same shape: a table.

## smaller than that

a `SELECT` doesn't even need a table. this is the smallest query there is, and it's a fine way to check that a connection works:

```sql run
SELECT 1;
```

the select list can hold any expression, and `AS` names the column it makes:

```sql run
SELECT 'hello' AS greeting, 6 * 7 AS answer, upper('ada') AS shouting;
```

and `*` means every column, in the order the table declares them. `ORDER BY id` sorts the rows and `LIMIT 5` keeps the first five; both get their own chapters later.

```sql run db=shop
SELECT *
FROM customers
ORDER BY id
LIMIT 5;
```

`*` is handy for looking around. in a program, name the columns: it's clearer, and it doesn't change under you when someone adds one. [picking columns](/learn/basics/select-and-expressions) has the rest.

## reading the result grid

the answer comes back as a grid, drawn the way psql draws one (more on psql in [psql and a real server](/learn/start/psql)). there's more in it than it looks:

<Figure caption={<>pick a part. these four customers are the shop's awkward ones on purpose: a missing email, a person actually named Null, and an empty city. the grid draws <code>null</code> faint and italic so it can't pass for text.</>}>
<GridAnatomy />

the same query, for real (press run and check the figure didn't lie):

```sql run db=shop
SELECT id, name, email, city
FROM customers
WHERE id IN (2, 10, 11, 42)
ORDER BY id;
```

NULL means "no value". `''` is a value that happens to be empty. `'Null'` is four letters. postgres keeps all three apart, and so should you: [NULL and three-valued logic](/learn/basics/null-and-three-valued-logic) is the chapter about the first one, and you'll want it sooner than you think.

## the semicolon

a semicolon ends one statement, so a block can hold several. each one runs on its own and gets its own result, numbered:

```sql run db=shop
SELECT count(*) AS customers FROM customers;
SELECT count(*) AS orders FROM orders;
SELECT name FROM products WHERE id = 200;
```

(product 200 is the left-handed teapot. nobody has ever ordered it.) the semicolon after the last statement is optional here and in most tools. in psql it isn't: psql sends nothing until it sees one.

you can ask postgres how it decided to answer. `EXPLAIN` shows the plan instead of running the query:

```sql run db=shop
EXPLAIN SELECT name, city FROM customers WHERE id = 42;
EXPLAIN SELECT name, city FROM customers WHERE city = 'London';
```

two questions with the same shape, two different hows. for `id = 42`, postgres walks the index that came with the primary key straight to one row (`Index Scan using customers_pkey`). for London there's no index on `city`, and 159 customers live there, so it reads the whole table and filters (`Seq Scan`). you didn't choose either one. tomorrow, with an index on `city` or ten times the data, it might choose differently, and your query wouldn't change. [reading EXPLAIN](/learn/execution/reading-explain) teaches the rest of those lines.

## spelling

keywords don't care about case, and neither do unquoted names: postgres folds them to lowercase before it looks them up. so this works:

```sql run db=shop
select NAME from CUSTOMERS where ID = 42;
```

this book writes keywords in capitals and names in lowercase, because it's easier to read, not because postgres minds. double quotes, though, turn folding off, so `"Customers"` means a table with a capital C, and there isn't one:

```sql run db=shop expect=error
SELECT name FROM "Customers";
```

which brings up the one rule that bites everybody once: **single quotes are for text, double quotes are for names**.

<Predict options={["customer 10, named Null", "customers with no name", "an error"]} answer={2}>
```sql
SELECT id, name FROM customers WHERE name = "Null";
```
<Explain>
`"Null"` in double quotes is a name, so postgres goes looking for a column called `Null`, doesn't find one, and stops. you wanted `'Null'`, in single quotes, which is a string. it's the same mistake as `WHERE name = "Ada Lovelace"`, and most people make it in their first week.
</Explain>
</Predict>

```sql run db=shop expect=error
SELECT id, name FROM customers WHERE name = "Null";
```

with single quotes it's a string, and customer 10 comes back. a single quote inside a string is written twice, which is how Sean O'Neil gets found:

```sql run db=shop
SELECT id, name FROM customers WHERE name = 'Null';
SELECT id, name FROM customers WHERE name = 'Sean O''Neil';
```

<Gotcha title="no ORDER BY, no promised order">
`SELECT name FROM customers LIMIT 3` gives you three customers, but which three is up to postgres. today it's the first three it stored. after an update, a vacuum, or a parallel scan on a big server, it can be any three. if the order matters, say `ORDER BY`. [LIMIT, OFFSET and FETCH FIRST](/learn/basics/limit-and-offset) shows how it goes wrong.
</Gotcha>

<Keylines>
- SELECT picks columns, FROM picks the table, WHERE picks rows, a semicolon ends it.
- the answer is always a table, with typed columns and a row count.
- NULL, '' and 'Null' are three different things, and the grid draws them differently.
- you say what. EXPLAIN shows the how postgres picked.
- single quotes for text, double quotes for names. unquoted names fold to lowercase.
</Keylines>
