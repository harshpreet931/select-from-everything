<InShort>
**autovacuum** is a background launcher that wakes up every `autovacuum_naptime` (a minute by default), checks every table's statistics, and starts a worker for each table past its **threshold**: 50 dead rows plus 20% of the table, by default. workers run slowly on purpose, against a **cost limit**, so they don't swamp the disk. it doesn't exist in this page's browser engine.
</InShort>

## the picture

you know how [VACUUM](/learn/mvcc/vacuum) is a command you have to run? nobody runs it by hand on a real server. something has to notice that a table has collected enough dead rows, and vacuum it without anyone asking, without hogging the disk, and without ever blocking the application.

think of a building's cleaning crew. a supervisor (the launcher) walks the floors every so often and checks each room's tally of mess (the statistics). rooms past their limit get a cleaner (a worker). cleaners work at a steady pace, stopping for a breather after every so many bins (the cost limit), so the building stays usable while they work. a big hall needs a big mess before anyone is sent, because the limit grows with the room.

first, honesty about this page. the engine running your queries is one process, and nothing runs in the background:

```sql run db=lab session=av
SHOW autovacuum;
SELECT backend_type, count(*) FROM pg_stat_activity GROUP BY backend_type ORDER BY backend_type;
```

the setting says on, and there's nobody to do it: one standalone backend, that's all. a real postgres 18.6 server, captured:

## the trigger

each round, for each table, the launcher compares the statistics system's count of dead rows (`n_dead_tup`) with:

```text
vacuum threshold = min(autovacuum_vacuum_max_threshold,
                       autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × reltuples)
```

the defaults are {cost.autovacuum_vacuum_threshold} and {cost.autovacuum_vacuum_scale_factor}, so 50 dead rows plus a fifth of the table. the cap is new in postgres 18 <Since v={18} />, at {cost.autovacuum_vacuum_max_threshold.toLocaleString("en-US")}. there are two more triggers on the same pattern: inserted rows (so insert-only tables still get vacuumed, for the [visibility map](/learn/storage/fsm-and-vm) and [freezing](/learn/mvcc/freezing-and-wraparound)), and changed rows for ANALYZE.

100 million. the formula says 200,000,050, but postgres 18 caps it with autovacuum_vacuum_max_threshold, 100,000,000 by default. on 17 and older the table really would wait for 200 million dead rows. either way that's a lot of dead rows to scan past, which is why big, busy tables get their own scale factor.
</Explain>

## going slowly on purpose

a worker charges itself for every page it touches: {cost.vacuum_cost_page_hit} for a page already in [shared buffers](/learn/storage/buffer-pool), {cost.vacuum_cost_page_miss} for one it has to read, {cost.vacuum_cost_page_dirty} for one it dirties. when the total reaches the cost limit ({cost.vacuum_cost_limit}, since `autovacuum_vacuum_cost_limit` is {cost.autovacuum_vacuum_cost_limit}, meaning "use vacuum_cost_limit") it sleeps for `autovacuum_vacuum_cost_delay`, {cost.autovacuum_vacuum_cost_delay} ms. and the limit is shared: with several workers running, each gets a proportional slice of it.

that's the right default for a background chore on a shared machine, and the wrong one for a table that's falling behind. a worker that dirties every page it visits manages {cost.vacuum_cost_limit / cost.vacuum_cost_page_dirty} pages per nap.

## the busy table it never reaches

the usual ways autovacuum loses:

- **the table is big.** 20% of a big table is a lot of dead rows, and a scan of a big table at a polite pace takes a long time. lower the scale factor for that table:

```sql run session=av
ALTER TABLE notes SET (autovacuum_vacuum_scale_factor = 0.01, autovacuum_vacuum_threshold = 1000);
SELECT relname, reloptions FROM pg_class WHERE relname = 'notes';
```

- **the workers are busy.** `autovacuum_max_workers` is {cost.autovacuum_max_workers}. three huge tables can occupy all of them for hours while everything else waits. postgres 18 lets you raise it without a restart, up to `autovacuum_worker_slots` ({cost.autovacuum_worker_slots}) <Since v={18} />.
- **it's too polite.** raise `autovacuum_vacuum_cost_limit` (say to 1000 or 2000 on decent storage), or lower the delay.
- **it can't remove anything.** a worker can be running constantly and still report "dead but not yet removable" for every row, because [a forgotten transaction](/learn/mvcc/xmin-horizon) is holding the horizon back. no setting fixes that.

`pg_stat_progress_vacuum` shows a running vacuum's phase and how far through the heap it is. `n_dead_tup`, `last_autovacuum` and `autovacuum_count` in `pg_stat_user_tables` tell you whether it's keeping up.

<Gotcha title="turning autovacuum off doesn't turn it off">
`autovacuum = off` stops the routine vacuums. it doesn't stop the anti-wraparound ones: once a table's oldest unfrozen xid gets older than `autovacuum_freeze_max_age`, a worker is started for it anyway. and where a normal autovacuum (which holds a [SHARE UPDATE EXCLUSIVE lock](/learn/locking/table-lock-modes)) steps aside when someone wants a conflicting lock, this one (it shows up as "(to prevent wraparound)" in pg_stat_activity) doesn't. people who disable autovacuum to "save I/O" get this vacuum later, all at once, at the worst time. see [freezing and wraparound](/learn/mvcc/freezing-and-wraparound).
</Gotcha>

<Interview q="when does autovacuum vacuum a table, and why might it fall behind?">
the launcher checks each table every autovacuum_naptime; a table is vacuumed when its dead tuple count exceeds autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × reltuples (50 + 20% by default, capped at autovacuum_vacuum_max_threshold since postgres 18), or its inserts exceed the insert threshold, or it needs freezing. workers throttle themselves with cost-based delays and share a cost limit. it falls behind on big tables (the 20% is huge), when all workers are tied up, when the cost limit is too low for the write rate, or when an old snapshot keeps dead tuples from being removable. bonus point: per-table storage parameters (ALTER TABLE ... SET (autovacuum_vacuum_scale_factor = ...)) are the usual fix for the big ones.
</Interview>

<Keylines>
- the launcher wakes every naptime; a table past 50 + 20% dead rows gets a worker.
- postgres 18 caps that at 100 million dead rows. inserts and changes for ANALYZE have triggers of their own.
- workers throttle themselves: page costs against a shared limit, then a short nap.
- big tables need a smaller scale factor. a stuck horizon needs a fixed transaction, not a setting.
- the browser engine has no autovacuum: every VACUUM on this site is one you can see.
</Keylines>
