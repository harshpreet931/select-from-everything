## why OFFSET is slow

OFFSET isn't a seek. postgres has no way to jump to "the 5,001st row" of a result: rows are numbered only as they come out of the plan. so it runs the query, counts rows off one by one, discards the first 5,000, and keeps the next 20:

```sql run db=events session=ks
CREATE INDEX events_at_id ON events (occurred_at, id);
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF)
SELECT id, user_id, kind, occurred_at FROM events
ORDER BY occurred_at, id
LIMIT 20 OFFSET 5000;
```

the Index Scan says `actual rows={fmt(scanned(2))}`. every one of those was fetched, heap page and all, so the Limit node could skip it. the index made the order free, but not the skipping. ([LIMIT and OFFSET](/learn/basics/limit-and-offset) has the semantics.)

so the next page is everything after `('2026-03-19 04:45:52+00', 5000)`, in order, 20 of it:

```sql run session=ks
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF)
SELECT id, user_id, kind, occurred_at FROM events
WHERE (occurred_at, id) > ('2026-03-19 04:45:52+00', 5000)
ORDER BY occurred_at, id
LIMIT 20;
```

`Index Cond: (ROW(occurred_at, id) > ROW(...))`: the whole comparison is an index search. one descent to the cursor, then 20 entries forward. the cost doesn't depend on how deep the page is, because nothing before the cursor is ever read.

## the row comparison is the trick

`(a, b) > (x, y)` is a row comparison, standard SQL: it means `a > x OR (a = x AND b > y)`, compared left to right like words in a dictionary. that's exactly the order of an index on `(a, b)`, so postgres can turn it into a single starting point in the index. write the same thing out longhand and it can't:

## the rules

- **the ORDER BY needs a tiebreaker that makes it unique.** `occurred_at` alone could have two events in the same second, and then "after the last one" would skip or repeat rows at the page boundary. ending on the primary key (`id`) fixes it, and the cursor carries both.
- **the index matches the ORDER BY and the comparison**: `(occurred_at, id)` for `ORDER BY occurred_at, id` and `(occurred_at, id) > (…)`. for newest first, flip all three: `ORDER BY occurred_at DESC, id DESC` with `(occurred_at, id) < (…)`; the same index serves it backwards.
- **mixed directions don't fit a row comparison.** `ORDER BY score DESC, id ASC` can't be written as one `(a, b) > (x, y)`. either use the OR form with an index declared `(score DESC, id)` and accept a filter, or put the columns in one direction.
- **the cursor travels with the page.** the client sends back the last row's `occurred_at` and `id` (often encoded into an opaque "next" token), not a page number.

## what you give up

you can't jump to page 251 directly; you can only go forward (or backward, flipping the comparison) from where you are. that's why infinite scroll, "load more" buttons and API cursors use keyset, and numbered page links use OFFSET. for numbered pages deep in a big result, people usually cap the depth, or precompute the page boundaries.

and a page can shift under you with OFFSET: if a row is inserted near the front between two requests, every later page moves by one, and you see a row twice. with keyset, page boundaries are values, not positions, so new rows before the cursor don't move what comes after it.

<Interview q="how would you paginate an API over a large, growing table?">
keyset (cursor) pagination: order by something unique, usually (created_at, id), and for the next page ask WHERE (created_at, id) > (last_created_at, last_id) ORDER BY created_at, id LIMIT n, with an index on (created_at, id). each page is one index descent plus n rows, no matter how deep. OFFSET reads and discards every earlier row, so it gets linearly slower, and rows inserted in between shift the pages. bonus points: the row comparison form is what lets postgres use the index as a range (the OR spelled out doesn't), and the cost is no random access to page k.
</Interview>

<Keylines>
- OFFSET n reads n rows and throws them away. deep pages get linearly slower.
- keyset: WHERE (a, id) > (last_a, last_id), with an index on (a, id).
- one index descent and n rows, on any page.
- write the row comparison, not the OR: only the row form becomes an index range.
- keyset can't jump to page k. it goes forward from a cursor.
</Keylines>
